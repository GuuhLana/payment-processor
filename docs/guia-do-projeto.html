Guia de leitura do código · projeto de estudo

Processador de Pagamentos

Uma API que recebe pedidos de cobrança, processa cada um em segundo plano contra um gateway simulado e guarda o histórico completo de tudo que aconteceu. Este guia percorre o projeto na ordem em que o código executa — do POST até a última linha gravada na auditoria.

O problema que o projeto resolve

Cobrar no cartão parece simples: chega o pedido, cobra, responde. Na prática, três coisas atrapalham — e cada uma delas explica uma parte da arquitetura deste projeto.

  • Cobrar é lento. Uma chamada a um gateway real leva de centenas de milissegundos a vários segundos. Se a API esperasse por isso, o usuário ficaria travado na tela e o servidor ficaria com conexões paradas sem fazer nada.
  • Cobrar é arriscado. Se o cliente clicar duas vezes, ou a rede cair e o app reenviar o pedido, você não pode cobrar duas vezes a mesma pessoa. Precisa existir um jeito de dizer "esta é a mesma cobrança de antes, não faça de novo".
  • Cobrar precisa ser explicável. Quando alguém pergunta "por que essa cobrança falhou?", saber só o status atual não basta. É preciso o histórico: quando entrou, quando foi para o gateway, o que o gateway respondeu e quando.

As respostas do projeto para os três, nessa ordem: processamento assíncrono via fila, chave de idempotência e tabela de eventos de auditoria. Todo o resto do código existe para sustentar essas três decisões.

O mapa: as camadas

O código está dividido em pacotes por responsabilidade. A regra que vale para todos: as camadas de fora conhecem as de dentro, nunca o contrário. O domain não sabe que existe HTTP, nem RabbitMQ, nem Stripe.

PacoteResponsabilidadeNão faz
api Traduz HTTP para chamadas de método. Recebe JSON, valida formato, devolve JSON e o código de status. Nenhuma regra de negócio.
service As regras de negócio. Decide se cria, se repete ou se rejeita um pagamento, e dispara o evento na fila. Não conhece HTTP nem SQL.
domain O que um pagamento é: seus campos, seus estados possíveis, seu histórico. Não conhece gateway, fila ou API.
repository Acesso ao banco. Interfaces do Spring Data — o SQL é gerado a partir do nome do método. Não decide nada.
gateway A conversa com os provedores de pagamento. Uma interface e várias implementações simuladas. Não grava no banco.
messaging Publica e consome eventos no RabbitMQ. É onde o trabalho assíncrono acontece. Não expõe nada por HTTP.
exception Erros de negócio e a tradução deles para códigos HTTP, num só lugar. —

Por que separar assim

Porque cada motivo de mudança fica isolado. Trocar Postgres por outro banco mexe só em repository. Adicionar um gateway novo mexe só em gateway. Mudar a rota da API mexe só em api. Se tudo estivesse numa classe só, qualquer uma dessas mudanças arriscaria quebrar as outras.

Por onde a mensagem viaja

Antes do passo a passo, vale ver o caminho físico. No RabbitMQ, quem publica nunca fala com uma fila diretamente: publica em um exchange com uma routing key, e o exchange decide em quais filas aquilo cai. Esta é a topologia montada por ConfiguracaoRabbitMQ:

payments.exchangetopic exchange
→ payment.requested →
payment.requested.queueOuvintePagamentoSolicitado
payments.exchangetopic exchange
→ payment.confirmed →
payment.confirmed.queueOuvinteResultadoPagamento
payments.exchangetopic exchange
→ payment.failed →
payment.failed.queueOuvinteResultadoPagamento
payments.dlxapós 3 retentativas
→ payment.requested.dlq →
payment.requested.dlqninguém consome — inspeção manual

Os nomes ficaram em inglês de propósito: exchange, queue, routing key e DLQ são o vocabulário padrão do protocolo AMQP, usado em inglês mesmo em documentação brasileira.

O fluxo completo, passo a passo

Aqui está a viagem de um único pagamento pelo sistema. A divisão em duas fases é a coisa mais importante desta página: a fase síncrona é o que acontece enquanto o Postman ainda está esperando a resposta; a fase assíncrona é o que acontece depois, sozinho, quando o cliente já foi embora.

Fase 1 · síncrona o cliente está esperando · alvo: poucos milissegundos
  1. ControladorPagamento.criar()

    Recebe o POST /pagamentos. A anotação @Valid checa o formato do corpo antes do método rodar: valor precisa existir e ser positivo, e moeda, gateway e chave não podem vir em branco.

    Se falhar aqui: nem chega ao service. O ManipuladorGlobalDeExcecoes intercepta e devolve 400 com o campo que deu problema.

  2. ServicoPagamento.criarPagamento() → ResolvedorGatewayPagamento.resolver()

    Primeira coisa que o service faz: confere se o gateway pedido realmente existe. Só stripe e pagseguro estão implementados.

    Por que logo no começo: um gateway inexistente é erro do cliente, não falha temporária. Se deixássemos passar, a mensagem entraria na fila, seria tentada quatro vezes e acabaria na DLQ — trabalho desperdiçado para um erro que dava para detectar na hora. Chamamos isso de falhar rápido.

  3. RepositorioPagamento.findByChaveIdempotencia()

    Procura se já existe um pagamento com aquela chave. Três desfechos possíveis: não existe (segue em frente), existe com os mesmos dados (devolve o que já existe, sem cobrar de novo), ou existe com dados diferentes (409 Conflict).

    O terceiro caso importa: se a mesma chave chega com um valor diferente, isso não é uma retentativa — é um bug no cliente. Aceitar em silêncio esconderia o problema; recusar deixa ele visível.

  4. repositorioPagamento.saveAndFlush() + registrarEvento()

    Grava o Pagamento com status PENDENTE e, na sequência, a primeira linha da auditoria: PAGAMENTO_SOLICITADO.

    Por que saveAndFlush e não save: força o INSERT a ir ao banco imediatamente, para que a violação da constraint UNIQUE apareça aqui e possa ser tratada — é a rede de segurança para duas requisições idênticas chegando no mesmo instante, que passariam as duas pelo passo 3 sem se enxergar.

  5. PublicadorEventoPagamento.publicarPagamentoSolicitado()

    Publica um MensagemPagamentoSolicitado no exchange com a routing key payment.requested. É aqui que o trabalho sai da requisição HTTP e vira trabalho de fila.

  6. → HTTP 201 Created

    A resposta volta com o pagamento ainda em PENDENTE. E está correto: o pedido foi aceito, não concluído. Nada foi cobrado ainda.

    É esse o contrato de uma API assíncrona: ela promete que vai processar, e entrega um id para você acompanhar. Quem consome precisa consultar depois (ou receber um webhook) para saber o desfecho.

Fase 2 · assíncrona ninguém está esperando · roda numa thread do listener
  1. OuvintePagamentoSolicitado.tratar()

    A anotação @RabbitListener faz o Spring entregar a mensagem a este método assim que ela chega na fila. Ele busca o pagamento, muda o status para PROCESSANDO e grava mais uma linha de auditoria.

  2. ResolvedorGatewayPagamento.resolver() → gateway.cobrar()

    O resolvedor devolve a implementação certa a partir do nome guardado no pagamento, e o método cobrar() é chamado. Este é o Strategy em ação: o listener não sabe — nem precisa saber — qual gateway está do outro lado.

    Nos gateways simulados há uma latência artificial e um sorteio: a maior parte aprova, uma fatia recusa por regra de negócio, e uma fatia pequena lança ExcecaoGatewayPagamento simulando um timeout de infraestrutura.

  3. publicarPagamentoConfirmado() / publicarPagamentoFalhou()

    O resultado vira outro evento na fila, em vez de ser aplicado direto. Isso simula o callback que um gateway real enviaria de volta, e mantém a etapa "decidir o desfecho" separada da etapa "chamar o provedor".

  4. OuvinteResultadoPagamento.aoConfirmar() / aoFalhar()

    Consome o evento de resultado, grava o status final (CONFIRMADO ou FALHOU) e a última linha da auditoria — incluindo o id da transação quando aprovado, ou o motivo da recusa quando não.

O desvio: quando o gateway cai de verdade

Existe uma diferença importante entre recusa e falha. Cartão sem saldo é uma recusa: o gateway respondeu, a resposta foi "não", e o pagamento vai para FALHOU — tentar de novo não mudaria nada.

Já um timeout é uma falha: o gateway não respondeu. Nesse caso a ExcecaoGatewayPagamento sobe para fora do listener, e o interceptor configurado em ConfiguracaoRabbitMQ reprocessa a mensagem com espera crescente entre as tentativas — cerca de 1s, 2s e 4s. Se as três retentativas se esgotarem, a mensagem vai para a payment.requested.dlq em vez de desaparecer, e fica lá para inspeção.

Os cinco conceitos-chave

Cada um resolve um problema concreto. Vale entender o problema primeiro — a solução fica óbvia depois.

1. Idempotência

o problema

O cliente clica em "pagar" duas vezes, ou a resposta se perde na rede e o app reenvia. Chegam dois pedidos idênticos e a pessoa é cobrada duas vezes.

a solução aqui

Quem chama envia uma chaveIdempotencia própria. A coluna tem constraint UNIQUE no banco, e o service consulta por ela antes de criar. Mesma chave e mesmos dados devolve o pagamento original.

A checagem em código e a constraint no banco parecem redundantes, mas não são: a consulta resolve o caso normal com uma mensagem de erro clara, e a constraint cobre a corrida entre duas requisições simultâneas, que o código sozinho não pega.

2. Strategy / Adapter nos gateways

o problema

Cada provedor cobra de um jeito. Sem cuidado, o código vira uma cadeia de if gateway == "stripe" ... else if ... que cresce a cada integração nova e espalha regras de provedor pelo sistema inteiro.

a solução aqui

Uma interface GatewayPagamento com cobrar(). Cada provedor é uma classe que a implementa. O Spring injeta todas num Map<String, GatewayPagamento> — a chave é o nome do bean — e o ResolvedorGatewayPagamento escolhe pelo nome em tempo de execução.

Consequência prática: adicionar um provedor novo é criar uma classe anotada com @Component("nome"). Nenhum if em lugar nenhum precisa mudar.

3. Mensageria assíncrona

o problema

Se a API esperasse o gateway responder, cada requisição seguraria uma thread por segundos. Um pico de tráfego derruba o serviço, e uma instabilidade do provedor vira instabilidade da sua API.

a solução aqui

A API só grava e publica um evento — trabalho de milissegundos. Um consumidor separado faz a parte lenta. Se o gateway ficar lento, as mensagens se acumulam na fila; a API continua respondendo normalmente.

4. Auditoria (event sourcing básico)

o problema

A tabela de pagamentos guarda só o estado atual. Quando algo dá errado, "está FALHOU" não conta quando cada etapa aconteceu, nem o que o gateway respondeu.

a solução aqui

Toda transição grava uma linha em eventos_pagamento. Essa tabela é append-only: nada é atualizado ou apagado, só inserido. Ler as linhas de um pagamento em ordem reconstrói a história inteira.

É "básico" porque num event sourcing completo os eventos seriam a única fonte de verdade e o estado atual seria calculado a partir deles. Aqui o status continua sendo uma coluna — os eventos convivem ao lado, como trilha de auditoria.

5. Retry com backoff e DLQ

o problema

Falhas de rede acontecem. Desistir na primeira tentativa perde pagamentos válidos; tentar em loop infinito trava a fila e ainda martela um serviço que já está em dificuldade.

a solução aqui

Três retentativas com espera crescente (backoff exponencial): ~1s, ~2s, ~4s. Esgotadas, o RepublishMessageRecoverer move a mensagem para a dead-letter queue, onde ela fica preservada para análise.

A espera cresce porque um serviço instável precisa de folga para se recuperar — retentar de imediato costuma piorar o problema que você está tentando contornar.

Os estados de um pagamento

Quatro estados, definidos no enum StatusPagamento. Os dois últimos são finais: um pagamento nunca sai de CONFIRMADO ou FALHOU.

PENDENTE → PROCESSANDO → CONFIRMADO FALHOU
EstadoQuem colocaSignifica
PENDENTE ServicoPagamento Pedido aceito e gravado. Ainda está na fila, nada foi cobrado.
PROCESSANDO OuvintePagamentoSolicitado Saiu da fila; o gateway está sendo chamado neste momento.
CONFIRMADO OuvinteResultadoPagamento O gateway aprovou. O id da transação fica registrado na auditoria.
FALHOU OuvinteResultadoPagamento O gateway recusou por regra de negócio. O motivo fica na auditoria.

Note que uma falha de infraestrutura não aparece nesta tabela: ela não muda o status. O pagamento fica em PROCESSANDO enquanto as retentativas acontecem, e continua assim se a mensagem for parar na DLQ — sinal de que precisa de intervenção humana.

Como rodar

São dois passos: subir as dependências em container e depois a aplicação. O banco e a fila precisam estar de pé antes. 

# 1. Postgres + RabbitMQ
docker compose up -d

# 2. a aplicação (porta 8080)
./mvnw spring-boot:run

# 3. conferir
curl http://localhost:8080/actuator/health

O painel do RabbitMQ fica em localhost:15672 (guest/guest) — é o melhor lugar para ver as filas enchendo e esvaziando enquanto você testa, e para inspecionar o que caiu na DLQ.

Para encerrar no fim do dia

Pare a aplicação com Ctrl+C e depois rode docker compose stop. Use stop, não down: os containers ficam desligados mas preservados, e no dia seguinte docker compose start já traz tudo de volta com os dados intactos.

Glossário

Os termos que aparecem no código e que costumam travar a leitura na primeira vez.

Idempotência

Propriedade de uma operação que pode ser repetida sem mudar o resultado. Executar uma vez ou cinco vezes dá no mesmo.

DTO

Data Transfer Object. Objeto que existe só para carregar dados entre camadas — aqui, entre HTTP e o service. Mantém o formato da API independente do formato do banco.

Record

Recurso do Java para classes imutáveis de dados. Uma linha define campos, construtor, equals e getters. Ideal para DTOs e mensagens.

Entidade / JPA

Classe anotada com @Entity que o Hibernate mapeia para uma tabela. Você mexe no objeto; ele gera o SQL.

Repository

Interface do Spring Data. Você declara o método com um nome padronizado e a implementação é gerada — findByChaveIdempotencia vira um WHERE chave_idempotencia = ?.

Exchange

No RabbitMQ, o ponto onde se publica. Ele roteia a mensagem para as filas de acordo com a routing key. Quem publica nunca escolhe a fila diretamente.

Routing key

O rótulo da mensagem (ex.: payment.confirmed) que o exchange usa para decidir o destino.

Queue

A fila onde a mensagem espera até um consumidor pegá-la.

DLQ

Dead-letter queue. Fila para onde vão as mensagens que falharam repetidamente. Guarda o problema em vez de descartá-lo.

Backoff exponencial

Estratégia de retentativa em que a espera dobra a cada tentativa (1s, 2s, 4s), dando folga a um serviço instável.

AMQP

O protocolo que o RabbitMQ implementa. É de onde vem todo esse vocabulário.

Constraint UNIQUE

Regra do banco que impede dois registros com o mesmo valor numa coluna. Aqui é o que garante idempotência mesmo sob concorrência.

Strategy

Padrão de projeto: várias implementações da mesma interface, escolhidas em tempo de execução. É o que permite trocar de gateway sem if.

Actuator

Módulo do Spring Boot que expõe endpoints de diagnóstico, como /actuator/health.
